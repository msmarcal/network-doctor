# Network Doctor

Diagnoses Juju Magpie network results. It reads `juju status --format json` from
a Magpie model, optionally alongside the CSV produced by the Magpie iperf action,
and reports ranked verdicts that name a likely cause and show the evidence behind
it.

## What it is for

Magpie tests connectivity between Juju machines across network spaces, but it
reports its findings as a sentence per unit. Reading a few dozen of those by hand
is slow, and the shape of a fault, one bad host against one bad VLAN against
jumbo frames missing end to end, is not visible from any single line.

Network Doctor parses those results, resolves the identifiers in them to actual
machines, correlates across spaces, hosts, MTU classes and availability zones,
and leads with what it concludes.

## Requirements

Python 3.8 or newer. Nothing else: the tool uses only the standard library, and
`python3` is part of the base Ubuntu system, so no installation step is needed on
a MAAS-provisioned or Juju-provisioned host.

## Usage

```bash
# from a file, with the iperf CSV discovered beside it
./network-doctor juju-status.json

# from a pipe
juju status --format json | ./network-doctor

# naming the iperf results explicitly
./network-doctor juju-status.json --iperf iperf.csv

# machine-readable output for other tooling
./network-doctor juju-status.json --json
```

Collect the inputs with:

```bash
juju status --format json > juju-status.json
juju run --wait magpie-internal-space/leader iperf   # writes the CSV on the unit
```

When `--iperf` is omitted and the status document was given as a file, the tool
looks for `iperf.csv` in the same directory and says in its header whether it
found one.

### Options

| option       | effect                                                        |
|--------------|---------------------------------------------------------------|
| `--iperf`    | path to the Magpie iperf CSV                                   |
| `--json`     | emit the normalized model, coverage and verdicts as JSON       |
| `--no-color` | never emit ANSI color, even on a terminal                      |

Color is emitted only when standard output is a terminal, so redirecting to a
file or piping into `grep` gives clean text without passing any flag.

### Exit status

| code | meaning                                          |
|------|--------------------------------------------------|
| `0`  | ran, and raised no verdicts                       |
| `1`  | the input could not be read or was not supported  |
| `2`  | ran, and raised at least one verdict              |

`2` makes the tool usable as a gate in a pipeline.

## Reading the report

### The coverage header

The first four lines say how much the run actually measured, and they matter as
much as the verdicts. Magpie only pings from every unit when `ping_mesh_mode` is
enabled; otherwise only the leader pings and every other unit reports
`icmp skipped`. A clean report from a leader-only run has measured almost
nothing, so the header states the coverage rather than leaving it to be inferred
from silence.

The same applies to parse accounting. Any status message the tool does not
recognize is counted in the header and printed in full at the end. It is never
dropped.

### Verdicts

Verdicts are ordered by blast radius, widest first, and each carries the
observations that produced it so you can disagree with the inference without
re-deriving the data.

The tool distinguishes several shapes of fault:

- one host failing across many spaces, which points at that host
- one space failing across all hosts, which points at its VLAN or binding
- failures confined to the spaces requiring MTU 9000, which points at jumbo
  frames not configured end to end
- failures confined to pairs that cross an availability zone, which points at the
  path between racks
- a pair that fails in one direction only, which points at a firewall or
  asymmetric routing rather than a layer 2 break
- DNS failing while ICMP is clean, which is a name resolution fault and not a
  network fault

### Throughput and what it can prove

The iperf action measures from the leader to each peer, a star rather than a full
mesh. A slow target therefore cannot be isolated on its own. The tool attributes
underperformance to a target host only when the same source reaches at least two
other targets at the peer rate over the same interface, which shows the common
path is healthy. When that cannot be shown, the finding is reported as an
observation naming no cause. Throughput is always compared within one space, so
spaces on a 1G management NIC are never measured against spaces on a 100G bond.

## Supported charm

The status grammar read here is the one produced by the reactive Magpie charm,
where the unit message is the ordered concatenation of six fields: port, bonds,
ICMP, local hostname, DNS and MTU.

The rewritten ops-based charm publishes `Ready, with N peers` and exposes results
through actions instead. The tool detects that form and reports the charm as
unsupported rather than reporting an absence of faults.
